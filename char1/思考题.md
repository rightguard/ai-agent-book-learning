1.  ★★ 如果你只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文还是更多的工具——你会选哪个？在什么条件下你的选择会改变？
回答：我会选择更强的模型，因为按照现有的趋势，更强的模型往往会拥有更长的上下文以及更多的工具支持，并且未来工具肯定是直接内化至模型的基本能力中；
如果在本地部署的情况下我的选择可能会改变，面对本地的针对性的任务例如包含隐私的长任务推理，我可能会优先选择更丰富的上下文或工具选择

2. ★★★ ReAct 循环中，累计缓存读取量随轮数近似二次方增长。如何降低这种增长？
回答：可以使用结果压缩、外挂记忆（例如RAG知识库等）、滑动窗口等方式。

3. ★★ “模型即 Agent” 范式意味着模型在工具调用决策上越来越自主。但本章论证了 Harness 工程的重要性反而在增加。这两个趋势如何共存？Agent 框架未来的核心价值体现在哪些方面？
回答：模型即agent的模式意味着模型在工具调用决策上自主性更强，而Harness工程则关注如何将模型的自主性与用户需求、系统资源等进行匹配、如何将有效算力应用到实处、限制模型的边界与行为。这两个趋势的共存，将为agent框架未来的核心价值提供支持。

4.  ★★ 消融实验中 “工具结果反馈” 的缺失会让 Agent 反复重试直到耗尽迭代预算。在生产环境中，除了工具结果缺失，还有哪些情况可能让 Agent 陷入这种循环？你会设计怎样的检测和终止机制？
回答：网络超时、参数错误、重复决策、上下文丢失均可能导致恶性循环；可通过重复调用检测、进展监测、重试限制和最大迭代次数实现安全终止。

5.  ★ 本章用感知、行动、策略三个维度分析了五个 Agent 产品。请选择一个你日常使用的 AI 产品，用这三个维度进行分析，并思考它的架构设计是否合理。如果由你来设计这个 AI 产品，有哪些改进空间？
回答：例如我在日常中经常使用的codex，架构设计的就很不错。当我发送需求和任务，它先会识别、读取内容，然后可能会询问我重点需要确认的地方，以最大程度匹配我的需求；codex在计划模式中，就是使用了“感知、行动、策略”的模式，先确认需求和编写计划，直至用户确认后再进行下一步；如果由我来设计这个产品，我可能会在codex的基础上，添加一些新的技能，例如在感知的搜索网络资料中重点挑选最相关、最能参考的信息，写代码时自动可以优先参考可用的开源代码

6.  ★★ 如果你要设计一个专门处理航班订票的客服系统，你会选择工作流模式还是自主 Agent 模式？有没有可能在同一个系统中混合使用两种模式？
回答：我会选择自主agent模式，因为航班订票是一个复杂的任务，各种情况多变，需要根据用户的需求和系统资源进行动态调整；如果在同一个系统中混合使用两种模式，我可能会在处理简单、固定的任务时使用工作流模式，而在处理复杂任务时使用自主agent模式。

7.  ★★★ 护栏部分提到了工具风险评级。如果一个工具在大多数情况下是低风险的，但在特定参数组合下变为高风险（如 `delete_file` 删除普通文件 vs 删除系统文件），你会如何设计动态风险评估？
回答：可以基于模型的历史情况，对工具的组合进行风险评估，根据评估结果动态调整工具的使用权限。（其实这个我也不太懂）

8.  ★★ 本章的 Agent 产品表格中，所有 Agent 的动作空间都是 “开放式” 的。一个受限的动作空间（比如只能从预定义选项中选择）在什么场景下反而优于开放式？
回答：在处理简单、固定的任务时，受限的动作空间可以减少模型的搜索空间，提高效率；而在处理复杂任务时，开放式动作空间有更大的的灵活性，可以尽可能不同的需求


9.  ★★ 人工干预机制要求 Agent 能 “优雅地移交控制”。但在实践中，用户可能不在线、响应很慢、或者给出模糊的指令。此时 Agent 应该怎么办？
回答：如果用户不在线、响应很慢、或者给出模糊的指令，agent应该能够自动切换到人工干预模式，等待用户确认后再进行下一步操作，这一般是最保险的做法；但是很多生产环境下的agent系统，用户可能无法及时响应，或者用户可能无法及时确认，这会导致agent系统无法正常运行，所以后面这个问题我还要探索探索

10.  ★★★ 引言指出 “好的设计原则应该穿越模型的迭代周期”，但实现这些原则的具体工程手段可能会随模型能力进步而过时。试举一个这样的 Agent 工程手段，并说明理由。
回答：例如，几年前很火的提示词工程，用精心手工编写复杂提示词引导模型工具调用，但现在随着模型自主规划和工具调用能力增强，这种方式逐渐被模型的自主决策取代了，但可靠执行的原则不会过时
