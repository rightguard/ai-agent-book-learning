【自测问题】
也欢迎你随时在群里抛出其他问题，自测题用于帮助理解，不要求一次答完。
1. “读取文件”和“删除文件”都操作文件，为什么设计重点不同？
回答：我觉得是因为两者的风险程度以及操作属性不同。
读取文件往往只是根据模型的需求，通过命令行/工具进行读取整份文件，一般不会对文件执行修改操作，不会改变文件的状态，属于“感知工具”，设计的重点主要在读取的准确性、上下文语义的完整性、读取效率、以及信息泄露风险方面；
而删除文件往往被视为是风险操作，属于“执行工具”，往往会直接改变文件的属性，造成不可逆的损失，这一步需要做很多的安全设置、权限、可恢复的考虑，需要在沙盒/隔离环境运行。


2. 一个工具描述只有“搜索相关内容”，你会补充哪些信息？
回答：分以下几个点展开吧。①应用场景：这个工具适合在哪些具体的场景使用，在哪些场景优先使用，最好也写一下在哪些场景不适用；
②权限设置：在哪些agent步骤/工作流状态可以使用或者不允许使用；
③输出格式约束：统一工具的输出的schema格式，可以给一个示例，并说明输出的结果是摘要还是全文；
④边界应用情况：可以举一些工具适用的边界，还可以举一些反例；
⑤输入参数与调用示例：明确输入的参数类型、必填字段、取值范围及格式约束，尽可能提供高质量的few-shot，降低参数生成错误的概率；⑥异常处理：补充工具的相应延迟、调用成本、结果数量以及各种情况的返回。


3. 工具返回“执行成功”，是否足以说明用户的任务已经完成？
回答：并不足以说明用户的任务已经完成，原因可以分成几个吧。
①执行成功不代表输出的结果符合用户的需求，可能工具的返回结果只是摘要/全文，不符合用户的需求；
②工具执行成功有可能是在超时、超用量、超权限的情况下完成的，这一点可能超出了用户的需求；
③工具执行成功返回的格式不一定符合json schema的格式化结构，可能导致阅读性比较差；
④执行成功不代表实际操作生效，比如代码文件修改完成，但是仍需要检查目标代码文件是否存在，并且是否正确修改完成。


4. MCP 的 Client 和 Server 分别承担什么职责？Tools、Resources、Prompts 各适合表达什么？
回答：mcp主要采用的是client-server架构。client负责与server建立通信、发现可用能力、发起工具调用及接收执行结果；server则负责实现并提供具体功能，向client提供标准化接口
关于Tools、Resources、Prompts：
①tools：主要用于执行具体操作，例如调用api、执行搜索功能、修改文件等，通常由模型根据任务需求决定是否调用；
②resources：主要用于提供数据和上下文，例如本地文档、数据库记录和知识库内容，通常由应用程序决定何时读取并提供给模型；
③prompts：主要用于封装可复用的提示词模板和任务流程，例如病例分析或审核模板，通常由用户主动选择使用


5. 发送邮件的工具超时了，为什么不能直接重试？你会先确认什么？
回答：为什么不能重试，我觉得有以下两个原因吧：
①超时不等于执行失败，邮件服务器可能已经成功接收或处理发送请求，只是由于网络延迟或响应丢失，导致agent未收到成功结果。此时直接重试可能造成重复发送；
②此类操作往往具有副作用或不可逆性，重复发送可能影响用户体验，甚至造成业务误解，因此不能简单套用普通只读工具的自动重试策略。
我会先确认：
①工具描述是否完善正确、工具执行是否完成、符合需求；
②检查工具是否支持幂等性机制，例如唯一请求 ID 和服务端去重，避免重复执行；
③工具检查完毕后，确认网络/其他状态无误，再检查邮件内容是否正确；如果发送状态无法确定，则可以先停止操作，必要时请求人工确认


6. 工具从 10 个增加到 1000 个时，全部提供给模型可能带来什么问题？
回答：①最直接的后果--上下文窗口爆炸，大量的工具描述、schema，占用大量token，可能导致模型无法正常工作，影响推理；
②模型不知道该选择哪些工具，难以识别准确的使用场景和能力边界，可能选择不合适的工具或者重复调用、漏调用，导致执行效率低、效果差；
③由于工具部分占用的token过大，可能会导致计算成本和推理延迟大幅增加，也会降低kvcache的复用效率；
④使用大量工具也会导致维护成本增加，不同的工具可能有不同的权限、风险、包含/以来关系，增加工具管理的复杂度
