1.★★ MCP 标准将工具定义从 Agent 框架中解耦了出来。但标准化也意味着复杂的工具交互模式（如流式输出、双向通信、有状态会话）可能难以在标准协议中表达。你认为 MCP 未来最需要扩展的能力是什么？
回答：因为MCP部分我接触的比较少，我就简单讲讲我自己的见解吧。题目中很多功能都已经实现了，我觉得在落地的场景中，未来mcp需要升级的应该是任务进度管理这一块，例如在复杂的多模型、多agent的任务执行中，工具的使用可能消耗很长的时间，最好是设计统一的任务进度管理机制，支持进度显示、取消、停止、预警等功能。


2.★★ 在 MCP 生态中，不同的 MCP 服务器可能提供功能高度重叠的工具。当 Agent 面对多个来源不同但功能相似的工具时，应该如何选择？如果不同来源的同名工具在行为上略有差异（比如一个返回摘要，另一个返回全文），Agent 是否有能力感知并利用这种差异？
回答：不同mcp服务器即使提供功能类似甚至同名的工具，但是适用场景、输入输出形式和执行能力也可能存在差异，因此agent不能仅根据工具名称进行选择，分为两个点展开吧
一、可以通过工具描述、输入输出的schema、任务能力边界以及高质量few-shot和反例，帮助agent理解不同工具的适用场景，尽可能去提升选择工具的准确率
二、agent可以结合实际调用结果和历史执行反馈，进一步识别工具之间的行为差异。例如，一个工具返回摘要，另一个返回全文，可以根据用户需要快速定位信息还是详细分析内容来动态选择。



3.★★ 本章提出了“执行-验证-反馈”闭环（如写代码后自动运行 linter）。这种“操作后立即自动验证”的模式还可以应用到哪些工具场景？是否存在某些操作，其验证本身的成本或风险超过了操作本身，导致这种模式不可行？
回答：“执行—验证—反馈”机制还可以应用于代码开发、文件管理、数据库操作、api调用、文档生成和rag检索等场景。例如，修改代码后执行linter和单元测试，修改文件后检查内容、文件hash、文件完整性，调用api后查询资源状态。
但这种机制并不适用于所有操作，以下举例几个不可行的案例吧。例如部分验证成本可能远高于执行成本，例如大型项目的代码的完整回归测试；一些操作具有副作用或不可逆性，例如支付交易、数据库删除，如果通过重复执行来验证，反而可能产生更大的风险。
在工程实现上，可能需要采用基于风险和成本的分层验证机制。对于低风险操作，可以立即自动验证；对于风险较高的操作，最好是结合幂等性和执行状态管理，避免验证失败或网络超时导致agent反复执行具有副作用的操作。


4.★★ 本章提出了“工具爆炸”问题——Agent 面对数千个工具时选择精度下降。除了主动工具发现，还有哪些方案？可以参考人类专家在面对大量可用工具时的策略。
回答：一、进行工具分层和分类管理，按照功能和应用场景、任务边界对工具进行分组，让agent先确定任务所属领域，再从对应工具集中进行选择，减少决策空间。
二、采用工作流模式，也就是sop，将高频且稳定的工具调用组合成可复用的工作流，减少重复规划和选择。
三、收集工具使用结果结果、反馈，根据工具的成功率、使用成本以及实际执行效果，形成工具偏好，并通过持续评估动态优化。
