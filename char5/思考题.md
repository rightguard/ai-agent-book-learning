1.★★ 代码生成被称为 Agent 的“元能力”。但代码执行引入了安全风险——Agent 生成的代码可能包含漏洞、无限循环或资源耗尽。沙盒隔离能解决部分问题，但也限制了代码能力（比如无法访问网络或文件系统）。如何在安全性和能力之间找到最优平衡点？
回答：因为在本章之前，我对沙盒的了解还是比较少的，学习了本章后，我对沙盒的了解有了更进一步的认识，所以我先谈谈我对沙盒的了解吧。我认为沙盒就是给agent一个受限制的独立环境，让它自己能够独立运行代码、进行测试，又不让它能够随意的操作计算机，尽量不影响外部的系统，只给一定的权限。
关于如何找到安全与能力的平衡点，我认为可以从以下几点展开吧：
①通过单独的容器（例如docker）或沙盒技术隔离代码执行环境，并限制cpu、gpu、内存、运行时间和文件系统访问权限，尽可能防止恶意代码执行，防止代码陷入无限循环。使代码的执行影响不会影响到宿主机器；
②遵循最小的权限原则，根据的任务的实时需求开放相应的权限，例如普通的计算可以直接在沙盒中执行，文件读取只允许访问指定的目录，网络请求最好是设置一定的接口，由权限或人工确认可执行；
③对于高风险操作例如删除、修改等，可以引入规则校验，或者llm-as-judege，甚至是人工确认，尽可能把风险降到最低。

2.★★★ Agent 自举——能创造 Agent 的 Agent——实现了“智能的自我繁殖”。但每次自举都可能引入新的偏差或错误，这种错误会在代际间累积吗？如何防止 Agent 自举的退化？
回答：偏差或错误的确可能会在代际间累积，这个可能与模型的权限和校准的设置会有关系。如何防止这种退化，我觉得可以从以下几点进行展开：
①在每次自举后，设置一定的规则校验器，只有当新功能/新工具/新代码/新输出通过校验器后，才能进行放行；
②利用llm-as-judge的机制，可以选择不同品牌/不同厂商的模型作为reviewer，在每次自举后判断是否有偏差和错误，可以及时纠正/提醒agent进行修正；
③执行跨代基准评估，使用固定的、独立的测试集，对比新旧agent的任务完成率、错误率、执行成本和安全性。只有满足关键指标且没有不可接受退化的新版本才能进入下一代；
④保留每一代agent的代码、配置、工具和测试记录，发现退化时及时停止自举，并恢复到已验证的稳定版本。
⑤当新的偏差和错误发生且agent难以自主判断和修复时，可以暂停流程，触发熔断机制，交由人工判断进行下一步。


3.★★ 代码生成 Agent 在处理日志解析时，能自动跟随格式演化。但如果格式变化是一个 bug 而非预期改动，Agent 的适应性反而掩盖了问题。Agent 应该如何区分“需要适应的变化”和“需要报告的异常”？
回答：可以从以下几个点讲一讲吧。
①在处理日志之前，可以先建立统一标准的schema和任务约束，明确哪些入参、字段是必须的，哪些变化是允许的，并结合变化前后的内容进行分析判断是否符合标注；
②当agent发现格式变化后，不应该立即修改代码或标准schema和约束，应该往回排查是否存在字段缺失、数据异常、解析结果异常等问题；
③引入规则校验机制，确保新代码不仅能够解析新的日志格式，也不会破坏原有功能；
④对于经过验证的正常变化，可以自动适配；对于疑似bug或无法确认的变化，应保留原始的日志和修改记录，及时报告异常，必要时交由人工

5.★★ 本章展示了 Coding Agent 把执行和调试中获得的经验沉淀回代码库的多种方式——写入知识库文件、更新架构文档、维护项目指令文件、把操作序列固化为代码。如果把这些经验进一步提炼为系统提示词中的规则，规则集会随时间不断膨胀。如何对沉淀下来的规则做“垃圾回收”——识别并清理冗余或过时的条目？为什么一次成功的代码修改还不能直接视为第九章所说的持续进化？
回答：对于第一个问题：
①为规则记录来源、时间、适用范围和历史验证结果，可以定期利用语义相似度、llm-as-judge和规则校验器识别重复、冲突及过时条目，并进行合并、更新或归档；②不用将所有经验都写入系统提示词，对于频繁使用、通用的提示词可以保留在系统层，写入系统提示词；对于在特定场景经常使用的工具/提示词，可以将项目特定规则放入项目文档，利用模型形成高质量的skills，将确定性约束写为代码；
③在清理规则前进行测试，并保留版本管理和回滚机制，防止删除重要规则造成能力退化

对于第二个问题：
①一次成功的代码修改并不能直接视为持续进化，因为它可能只是针对当前任务的局部修复，甚至可能存在偶然成功或过拟合的问题，并不能证明agent已经获得了可迁移、可复用的新能力；
②真正的持续进化需要将执行经验进行评价、归纳和验证，再将有效经验沉淀为知识、规则、skills或者代码，并在后续任务中正确使用。最好建立高质量的、可复用的测试集、跨任务评估及回归测试，验证新能力是否真正提升任务完成率、泛化能力与执行效率，以及是否破坏原有的功能。

8.★★ Artifact 模式让 Agent 生成 SQL 或前端代码，由数据库和浏览器直接执行，绕过 LLM 处理大量数据。与传统的“Agent 直接给出答案”相比，这种“Agent 生成代码、系统执行代码”的分工有什么优劣？生成的 SQL 可能执行破坏性操作、生成的 HTML 可能包含漏洞，又该如何确保安全？
回答：优势：主要体现在执行效率、token成本和计算准确性方面。通过让agent生成sql或前端代码，再交给数据库、浏览器等专业引擎执行，可以避免llm直接处理大量数据，同时利用专业引擎的计算与渲染能力，提高执行效率。
劣势：生成代码可能存在语法或逻辑错误，导致执行失败或结果不符合预期；此外，直接无权限限制的代码执行还可能带来数据库破坏、恶意脚本执行和敏感信息泄露等安全风险

因此，可以采用沙盒隔离、最小权限、代码检查和执行验证相结合的机制。对于sql，默认限制为只读查询，对于修改、删除等风险操作给予限制，并结合语法校验、资源限制和高风险操作审批；对于html，则通过浏览器沙盒、内容安全策略和输入清理降低安全风险。


9.★★ 将业务规则编码为工具内部基于数据库真值的校验，并用参数设计引导模型在调用前核对政策条件，本质上是用代码结构来约束 Agent 行为。这种“代码即规则”的模式相比自然语言规则有什么优势和局限？
回答：优势：
①“代码即规则”相比自然语言规则，最大的优势是具有更强的确定性、一致性和强制约束能力；
②自然语言规则依赖模型自身理解和遵守，可能存在遗漏或解释偏差，而代码规则可以在工具执行层强制校验，可以阻止不符合条件的操作；
③代码规则具有更好的可测试性和可追溯性，可以通过单元测试、回归测试和执行日志保证规则的可靠性。

局限
①代码规则灵活性较低，往往难以完整表达复杂、模糊或存在例外的业务条件
②其次，如果代码实现错误、数据库信息不准确或规则未及时更新，也可能产生系统性错误。
