1. 能生成一段代码的聊天助手，与 Coding Agent 的关键区别是什么？
回答：能生成代码的聊天助手，往往只是根据当前的上下文/临时的用户需求进行生成的，一般获取上下文的信息能力有限，而且生成的代码一般很少会自主检查、自主测试，往往需要用户自行执行、测试和反馈错误。
而coding agent不仅能够主动检索现有的文件和代码库、理解项目架构和依赖关系，还能够根据任务需求制定执行计划，通过文件系统和终端工具直接修改代码、运行程序，并利用linter等工具检查代码质量和语法，当执行失败时，可以根据错误信息自主定位问题并迭代修复。


2. “文件写入成功”“程序能运行”“用户需求已满足”，为什么是三种不同的判断？
回答：以代码文件为例吧：
“文件写入成功”代表代码创建/编辑完成，并不代表代码通过可行性测试、语法都正确，所以不一定能运行，也不代表用户需求已经满足；
“程序能运行”代表代码能够运行、输出，但是输出的结果、传入参数可能没有符合用户的需求，例如程序可以输出json格式的结果，但是输出的json schema和原先定义的不符；
“用户需求已满足”代表用户的需求得到完善、任务已经完成，表明程序不仅能够正常运行，还通过了功能测试、业务规则校验、结果验证等流程，是基于前两者基础上完成的，是最理想的状态。


3. 为什么说代码可以是“创造新工具的工具”？请举一个非编程任务的例子。
回答：代码具有很强的通用性和可组合性，不仅可以完成当前的用户的指定的任务任务，还可以根据实际需求创造新的工具。比如，在医疗病例质量评审中，原先的agent发现现有工具无法自动关联相关的信息，就可以自主生成代码程序，将数据提取、字段匹配和异常检测封装为专用工具，经过测试验证后供后续任务重复调用。这使agent从单纯使用预定义工具，进一步发展为能够按需扩展自身能力的系统。



4. 如果 Agent 连续修改三次仍然测试失败，你希望它接下来检查什么，而不是继续盲改？
回答：如果agen连续修改三次仍然测试失败，可以检查以下几个部分：
①模型调用是否成功且正确、上下文窗口是否满足当前任务需求，记忆是否正确；
②工具是否调用正确，工具的定义和描述、使用场景是否正确；
③任务的本身是否描述错误、描述不完整、或者描述的边界不清楚，agent没有读懂用户的意图，可以提供一些高质量的few-shot；
④上下文语义、代码库是否有危险/漏洞文件，导致上下文语义被污染，导致执行错误；
⑤检查执行环境和工具调用，包括依赖版本、路径配置、测试命令以及工具参数是否正确；



5. 什么情况下应该让代码执行计算或数据处理，而不是让模型直接给出答案？
回答：我认为当任务涉及复杂计算、大规模数据处理、多步骤逻辑操作、高精度要求或重复性工作时，更适合让agent生成代码并交由程序执行，而不是依赖模型直接给出答案。因为python/sql/html/css等执行引擎能够高效、确定性地完成计算和数据处理，降低token消耗，并支持结果验证与代码复用。但需要注意，代码本身也可能存在逻辑错误，因此应结合单元测试、数据校验和执行反馈机制，确保最终结果正确。对于简单且无需精确计算的任务，模型直接回答通常更加高效。
