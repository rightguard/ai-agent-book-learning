1. ★★ 共享上下文的多 Agent 协作中，后续 Agent 继承了前序 Agent 的完整上下文。但前一个 Agent 积累的“思维惯性”可能影响后续 Agent 的判断——比如继承了“需求分析师”上下文的“代码审查员”，可能还是倾向于从需求角度思考而非代码质量角度。如何检测和消除这种角色间的干扰？
回答：
①在检测方面，可以采用控制变量实验，分别设计完整共享上下文、结构化共享上下文和独立上下文三组方案，在相同任务下比较后续agent的判断质量、职责符合程度和错误检出率。同时，可以构造前序agent给出错误判断的测试用例，检查后续agent是否存在盲目接受前序结论的情况。
②在缓解方面，首先为不同agent设置独立的角色提示词、工具权限和评价标准，明确各自的职责边界。其次，可以通过结构化上下文交接，只传递必要的任务信息、约束和客观证据，减少历史推理与主观判断的干扰。
此外，还可以引入proposer-reviewer机制，使用独立上下文甚至不同模型家族的reviewer，对前序agent的结果进行交叉评审，并结合实际工具执行结果、测试和静态检查等外部证据进行验证。


2. ★★ 管理者模式中，Manager Agent 负责任务分解和结果整合。但 Manager 本身的能力上限决定了整个系统的能力上限——如果 Manager 无法正确分解任务，子 Agent 再强也无用。如何确保 Manager 的分解质量？
回答：可以从四方面提高manager的任务分解质量，分别是提示词质量、上下文管理策略、任务分解颗粒度、动态验证。
①提示词质量：这个和前几章的内容是直接挂钩的，manager的系统提示词的质量决定了它的行为和思路，可以从提供高质量的范例、反例、边界情况、few-shot、结构化内容等方面，明确manager的职责，要求manager在规划agent协作时需要认真思考整体的目标、任务约束、子任务依赖以及相关的验收标准；
②上下文管理策略：可以通过分层上下文、结构化摘要、按需检索等机制，确保manager能够准确理解用户需求和当前的任务状态，避免由于上下文的过载和信息确实导致manager进行错误规划；
③任务分解颗粒度：粒度过大→子agent可能难以完成，出现上下文过载；粒度过小→agent间通信频繁，token和协调成本增加；粒度合理→子任务职责明确、依赖清晰、结果可以独立验证；需要平衡子任务的复杂度和agent之间的协作成本，每个子任务尽量拥有明确的任务目标、清晰的职责、规范的输入输出和独立的验收条件，同时根据任务依赖关系合理安排串行或者并行；
④可以引入proposer-reviewer机制，对manager生成的任务计划进行独立审查，并在实际执行过程中根据子agent的反馈、工具执行结果和任务验收情况动态调整计划。



3. ★★ 去中心化模式借鉴了人类组织的最佳实践。但人类组织也有大量失败模式——沟通不畅、责任推诿、目标冲突。你认为 Agent 社会中最可能出现哪些“组织病”？如何预防？
回答：
去中心化的多agent架构虽然能够提高系统的自主性和协作灵活性，但也可能出现与人类组织类似的组织病。
①信息沟通不及时、语义冲突：例如，一个agent负责重新编排文档图片编号，另一个agent同时使用原始编号修改正文。虽然两者没有直接修改相同文件，但最终可能出现引用错误。这个错误，可以通过任务依赖管理、共享文件版本控制、变更通知和跨文件一致性校验来减少冲突；
②错误连续、逐层传播：agent之间频繁传递摘要和结论时，错误可能被逐层放大。可以引入独立reviewer、原始证据溯源和关键步骤验证，避免后续agent仅依赖前序agent的判断。
③执行循环和资源失控：部分agent可能不断创建子agent，或者在失败后重复调用工具，导致token和计算资源消耗不断增长。对此，需要在harness层设置整个任务树的预算上限、最大并发数、递归深度、超时和熔断机制，必要时触发级联取消。
④职责和权限边界模糊：多个agent可能重复执行同一任务，或者越权修改其他agent的成果。因此，应为每个任务明确负责agent、输入输出、验收标准和权限范围，并通过任务状态管理、最小权限及幂等性控制避免重复操作。
④目标冲突和责任扯皮：不同agent可能基于各自的局部目标做出相互矛盾的决策。对此，需要事先定义全局目标与约束优先级，并在发生冲突时使用规则仲裁、独立审核或人工介入等机制。



4. ★★★ 在管理者模式中，当多个子 Agent 并行执行时，一个子 Agent 的发现可能使其他子 Agent 的工作变得毫无意义（比如搜索任务中一个 Agent 已经找到了答案）。设计一种高效的级联终止机制，实现“一个成功，全员停止”。
回答：可以采用事件驱动、共享任务状态和级联取消机制，实现管理者模式中“一个成功，全员停止”的目标。
①manager在任务开始时创建统一的任务组，为各子agent分配任务id，并明确成功条件、执行预算和取消规则；
②各子agent异步执行任务，当某个agent找到候选答案时，立即通过消息总线向manager发送事件，并提交结果和相关证据；
③manager不能直接依据子agent自行声明的成功状态终止其他任务，而应该通过独立验证器（或者外部的reviewer）确认结果满足要求。验证成功后，采用原子状态更新机制提交最终结果，避免多个 Agent 同时成功造成竞争冲突；
④manager向任务组内其他agent广播取消信号，要求它们停止新的工具调用，并将取消信号继续传播至下级子agent，同时释放计算资源、记录执行状态；
⑤可以引入两阶段终止策略，在候选答案出现时暂停不必要的新任务，验证成功后再正式级联取消。同时设置取消超时、强制清理和幂等性机制，处理异常情况。



5. ★★★ 本章介绍的乐观锁机制解决了单文件的并发写入冲突，但实际的多 Agent 系统中，共享文件系统还面临跨文件的语义冲突、命名空间污染（Agent 随意创建文件导致目录混乱）和单点故障（一个 Agent 错误地删除了所有文件）等问题。你会如何设计更完善的文件系统治理机制？
回答：多agent共享文件系统的治理不能仅依赖乐观锁，还应该从工作空间隔离、语义一致性、权限控制和故障恢复四个方面进行设计。
①工作空间管理：为不同的agent分配独立目录或git worktree，通过统一的命名规范、文件索引和临时文件清理机制，避免命名空间污染与直接写入冲突；
②跨文件语义一致性：可以建立文件依赖关系和变更通知机制。当某个agent修改公共数据或文件结构时，及时通知manager以及依赖该资源的其他agent。同时，在合并阶段增加自动化检查，验证跨文件引用、数据一致性和业务逻辑是否正确，而不只是检查文件版本冲突；
③权限控制：，应采用最小权限原则，限制各agent的文件读写范围，对批量删除、覆盖共享文件等高风险操作设置审批和保护机制，避免单个agent的错误操作破坏整个工作空间；
④结合git版本管理、文件快照、执行日志和回滚机制，确保每次修改都能够追溯和恢复。对于多个agent的修改，应通过统一的验证与提交机制，确认无冲突后再发布到正式共享空间。



6. ★★★ 基于市场机制的 Agent 协作（Pinchwork、RentAHuman）引入了交易关系：一个 Agent 花钱雇佣另一个 Agent（或人类）完成任务。那么，雇主 Agent 如何自动衡量执行者交付的结果质量？如果执行者声称已完成但雇主认为质量不达标，争议由谁仲裁？如何防止劣币驱逐良币？
回答：可以采用proposer-reviewer机制作为agent交易市场的核心质量验证方式，但还需要结合任务契约、独立仲裁和信誉机制进行完善。
①质量评估：交易开始前应明确任务要求、验收标准和rubric。执行者完成任务后，可以通过确定性测试、外部证据验证和独立reviewer进行综合评估。对于代码类任务优先采用程序化测试，对于开放式任务则结合llm-as-judge与人工校准；
②争议仲裁：不能让雇主agent单方面决定执行者是否获得报酬。可以采用资金托管与独立仲裁机制，当双方出现争议时，由第三方依据原始任务契约、交付成果和执行证据作出判断。对于高价值交易或者涉及真人劳动的争议，应允许人工仲裁和申诉；
③防止劣币驱逐良币：可以建立基于真实验收结果的信誉体系，综合考虑执行者的质量、价格、准时交付率和历史争议情况。同时，通过异常交易检测、信誉审计和合理的市场匹配机制，减少刷单、虚假评价和恶性低价竞争。



7. ★★ RentAHuman 让 Agent 通过加密货币雇佣人类，反转了传统的人机关系。如果这种模式普及，人类在 Agent 经济中扮演什么角色？仅仅是执行 Agent 无法完成的物理任务吗？
回答：如果 RentAHuman 这种agent雇佣人类的模式逐渐普及，人类在agent经济中并不会仅仅扮演物理任务执行者的角色，而是可能形成更加多元化的分工。
①人类可以直接执行物理操作，帮助agent完成实地考察、设备维修等需要现实世界操作的任务。
②人类还提供专业知识、辅助决策，尤其是在医疗、法律、工程等复杂领域提供专业判断，弥补agent在特定情境下的能力不足。
③人类可以承担质量监督和仲裁，例如，结合之前讨论的proposer-reviewer机制，对agent的任务成果进行人工复核，并在交易双方发生争议时提供独立判断。
④人类还是agent执行规则的制定者：agent可以承担任务规划、资源分配和执行协调，但不应该因此获得无限制的决策权。涉及法律责任、伦理判断及个人权益的问题，仍然需要明确人类或组织的责任边界。
⑤需要防止人类被简单地工具化，通过合理的报酬机制、任务授权、知情同意、安全保障和争议处理机制，保护人类执行者的权益。



8. ★★ 人类社会需要多人分工协作，是因为每个人的能力有限——做前端的不一定懂后端，懂设计的不一定会运维。但大模型更像一个“全才”。相关研究表明，在纯文本推理任务上，多 Agent 辩论在等量计算资源下并不优于单 Agent。那么，使用多个 Agent 而非单个 Agent 的真正优势到底在哪里？
回答：多 Agent 相比单 Agent 的真正优势，并不只是将多个模型组合起来提高推理能力，而是通过分工协作、独立验证、并行执行和上下文隔离，提高复杂任务的执行效率与可靠性。
①任务规划：可以将复杂任务拆解为多个职责明确、具有独立验收标准的子任务，由不同agent分别执行，降低单个agent的任务复杂度；
②任务审核：可以采用proposer-reviewer机制，让独立reviewer结合代码测试、工具执行结果和其他外部证据，对前序agent的成果进行验证，减少错误传播和自我确认偏差；
③并行执行：可以让多个agent同时探索不同方案或完成相互独立的子任务，从而缩短整体任务耗时，提高搜索与探索的覆盖度；
④上下文管理：不同agent可以维护独立的上下文、角色和工具权限，减少上下文膨胀与角色间干扰，并通过结构化消息完成协作；
不过，多agent也会引入额外的通信、协调和计算成本，因此不能认为agent数量越多越好。应当根据任务是否能够有效拆分、是否需要独立验证，以及并行收益是否超过协作成本来决定是否采用多agent。



9. ★★★ 本章将“共享上下文”与“不共享上下文”作为多 Agent 系统的核心设计维度。共享上下文让所有 Agent 看到相同信息，似乎更利于协调。但《三体》中的三体人思维完全透明，技术发展却陷入停滞；回形针思想实验也表明，当群体趋向同一目标时，多样性随之丧失。在多 Agent 系统中，如何在效率与多样性之间找到平衡？
回答：多agent系统需要在信息共享效率和独立思考能力之间建立动态平衡，不能简单地采用完全共享或完全隔离的上下文策略。
①在上下文管理方面，可以采用选择性共享机制，让不同agent共享任务目标、约束条件、客观证据和执行状态，但对未经验证的假设、中间推理和探索路径保持相对独立，减少上下文锚定和群体趋同；
②在协作流程方面，可以采用“先独立探索、再结构化共享、最后交叉验证”的机制。不同agent先分别提出方案，再通过共享文件系统或消息总线交换必要的结果和证据，最终利用独立reviewer和外部工具进行验证；
③可以通过不同模型家族、差异化角色提示词、工具配置和信息来源，增加agent之间的认知多样性，降低同质模型产生相同错误的风险；
④应当根据任务特征动态调整共享程度。对于任务依赖较强、目标明确的场景，加强信息同步；对于科研探索、复杂推理和开放式问题，则增加独立探索。通过控制变量和消融实验，综合评估任务成功率、方案多样性、token成本和执行效率。



10. ★★★ 给一个 Coding Agent 分配 30 步预算和 300 步预算，它的工作策略应该如何不同？研究表明，单纯增加步骤预算并不能保证性能提升——Agent 会在浅层搜索后过早“饱和”。设计一种“预算感知”机制，让 Agent 在小预算下快速实现核心功能，在大预算下增加规划、测试和审查环节，充分利用额外的计算资源。
回答：可以在harness中引入预算感知控制器，根据coding agent的总预算、剩余预算和实际任务进展，动态调整任务规划、代码实现、测试与审查策略。

①对于30步的小预算，应优先实现核心功能，采用较为直接的执行策略，减少不必要的方案探索，但仍然需要保留必要的测试和结果验收步骤；
②对于300步的大预算，则可以进行更充分的需求分析、方案比较和模块化设计，并增加单元测试、集成测试、边界测试、错误修复以及独立reviewer审查等环节，提高任务完成质量和可靠性。

预算控制器不仅需要跟踪剩余步数，还应综合考虑 Token 消耗、执行时间、任务完成度和每次工具调用带来的信息增量。随着预算减少，agent应逐步从广泛探索转向重点实现、修复与验收。
此外，为防止agent在浅层搜索后过早饱和，可以结合执行日志、测试结果和失败归因判断任务是否持续取得进展。当连续多次操作没有带来有效改进时，应触发重规划、调整探索方向或独立审查，而不是盲目增加执行次数。
最后，通过控制变量实验，对比不同预算下普通agent与预算感知agent的成功率、token成本、测试覆盖和实际执行步数，验证预算感知机制是否真正提高资源使用效率。



11. ★★ 本章对比了多 Agent 系统与操作系统。虚拟内存与分页、文件权限、死锁检测、调度算法，各对应 Agent 世界的什么？又有哪些操作系统概念在 Agent 世界找不到对应物，为什么？
回答：多agent系统可以借鉴操作系统的资源管理与进程协作机制，但由于agent的执行具有语义性和不确定性，两者并不能完全对应。
①虚拟内存与分页：可以采用分层上下文、外部记忆和按需检索机制，将当前任务相关的信息保留在上下文中，其他信息存储在外部文件系统，需要时再动态加载，以降低token 消耗和上下文膨胀；
②文件权限：可以通过独立工作区、最小权限原则、工具白名单和沙盒隔离，限制不同agent对共享资源的访问与修改权限，避免越权操作和文件污染；
③死锁检测：可以维护agent之间的任务依赖图与等待状态，检测循环依赖、超时和无效通信，并通过任务重规划、依赖解除或人工仲裁恢复执行；
④调度算法：可以根据任务优先级、依赖关系、执行预算和资源占用情况，动态调整agent的执行顺序、并发数量以及token分配，提高整体执行效率；

不过，操作系统中的部分机制无法直接映射到agent世界。例如，硬件级内存隔离和自动缺页机制无法直接解决llm的语义遗忘；抢占式调度也不能保证模型推理能够在任意时刻无损暂停和恢复。另外，传统操作系统能够管理进程状态，但无法判断agent输出内容的语义正确性。
