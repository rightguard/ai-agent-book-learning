1. 把一个提示词拆成四个角色，是否就一定比单 Agent 更好？
回答：不一定，需要根据具体任务的复杂度、可分解性和执行成本进行判断。
如果任务目标明确、步骤较少、逻辑简单，单agent通常能够以更低的token成本和通信开销完成任务，此时拆分成多个角色反而可能降低效率；
如果任务较为复杂，并且能够拆分为职责明确、相对独立的子任务，那么多agent可以通过任务分工、并行执行和独立上下文管理提高效率。

此外，如果不同agent能够使用不同工具获取新的信息，或者通过proposer-reviewer机制结合外部证据进行独立验证，那么多agent可能进一步提高任务的准确性和可靠性。
但多agent也会增加协调成本、token消耗以及错误传播的风险。因此，不能仅凭提示词长度或角色数量判断方案优劣，而应该在相同预算下，通过任务成功率、执行时间、token成本和结果质量等指标进行对比。


2. 共享上下文与独立上下文，各可能出现什么信息管理问题？
共享上下文：①上下文膨胀问题：随着多个agent不断执行任务，历史消息、工具调用结果和中间推理持续累积，可能增加token成本，并导致当前agent难以关注重要信息；
②角色干扰问题：即使不同阶段切换了系统提示词，后续agent仍可能受到前序agent思考方向的影响。最后是错误继承问题，前序agent的错误结论可能被后续agent直接接受，从而导致错误逐层传播。因此，可以采用上下文压缩、动态角色切换和独立验证机制进行缓解。

独立上下文：①信息同步：不同agent维护独立的执行轨迹，可能对任务进度和状态产生不一致的理解。
②信息丢失和重复：agent之间通过摘要、文件或消息传递信息时，可能遗漏关键细节，或者出现消息重复、乱序等问题。
③调试困难：系统需要关联多个agent的日志，才能还原完整的任务执行过程。因此，需要设计结构化通信协议、统一的任务状态管理、消息幂等性机制和分布式追踪日志。

综上，共享上下文的核心挑战是信息过载、角色干扰和错误继承；独立上下文的核心挑战是信息丢失、状态不一致和协作追踪困难。 应当根据任务特点选择合适的上下文架构，并通过harness层面的上下文管理、通信协议和验证机制提高系统可靠性。

3. 多个 Agent 共享一个文件夹，是否等于它们共享完整对话上下文？
回答：不一定。多个agent共享文件夹，只代表它们能够通过文件系统交换信息，并不意味着共享完整对话上下文。
①文件访问权限决定各agent能够读取和修改哪些文件；
②即使拥有读取权限，也需要主动调用工具读取文件，相关内容才会进入当前agent的上下文；
③完整的对话上下文还包括历史消息、工具调用记录和执行轨迹等，这些信息不会因为共享文件夹就自动同步。


4. Reviewer 只阅读结果，与实际运行测试或核查来源，有什么区别？
回答：①reviewer只阅读proposer的结果，主要依靠模型自身的推理能力进行审核，虽然能够发现部分逻辑和格式问题，但可能受到前序错误结论的影响，缺乏独立的验证证据。
而实际运行测试或核查来源，可以引入外部反馈。例如，通过单元测试发现程序运行错误，通过核查原始文献和数据验证结论的真实性。
因此，proposer–reviewer机制不应只依赖llm之间的相互评价，而应该根据任务特点结合自动化测试、原始证据核查和独立reviewer，提高审核结果的可靠性。


5. 一个子 Agent 超时，或两个 Agent 给出矛盾结论时，主 Agent 应该如何处理？
回答：可以通过状态监控、独立验证、故障恢复和动态重规划机制处理这两种问题。
①当子agent超时时，主agent应通过执行日志和任务状态判断超时原因，检查任务是否已经部分完成。如果只是临时故障，可以在预算允许的情况下进行有限重试；如果持续失败，则可以取消任务、恢复检查点或重新分配给其他agent。同时，应结合幂等性机制，避免重复执行产生副作用；
②当两个agent给出矛盾结论时，主agent不应该直接选择其中一个结果，而应对比双方的原始证据和判断依据。可以采用proposer–reviewer机制，引入独立reviewer，并结合工具执行结果、测试或原始数据进行交叉验证。如果仍然无法确定正确结果，可以继续收集证据、重新规划任务，必要时由人工处理；
③整个过程应记录执行日志、冲突原因和处理结果，并设置重试次数、时间及token预算上限，防止agent陷入无限重试或无效讨论。


6. 请分别举出一个适合多 Agent 和一个更适合单 Agent 的任务，并说明理由。
回答：开发一个具有多个相对独立模块的复杂软件系统比较适合多agent。可以通过manager进行任务规划，让多个workers并行负责前端、后端等模块，再通过独立reviewer和实际测试结果进行验证。这样可以充分发挥任务分工、并行执行、上下文隔离和交叉验证的优势。

而修复一个简单的python脚本则更适合单agent。因为任务目标明确、上下文较少、执行步骤简单，单agent就能完成问题定位、代码修改和测试验证。如果拆成多个 agent，反而会增加通信、调度和成本。
