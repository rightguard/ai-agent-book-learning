1.  ★★★ 实验 2-3 发现，滑动窗口对话历史会导致 Agent 反复执行相同的工具调用。但完整保留历史又会让上下文不断膨胀。设计一种策略，既能避免信息丢失，又能控制上下文长度，且不破坏 KV Cache 前缀。
回答：我感觉策略需要有三个要点：①固定的前缀：保障system prompt的核心规则是不变的，这样可以保证agent可以最大化复用kvcache；②定期整理：定期将历史对话压缩，抽取主要的关键信息、任务进度、关键工具记录和结果，形成结构化记忆，避免重复执行；③外部记忆：可以将②中的内容储存到磁盘/其他介质，这一步有点类似于RAG的思想，把重要信息保存成固定的文件，在agent需要时可以检索调用

2. ★★ Qwen3 的 Chat Template 思维链保留机制只保留 “最后一个真实用户消息之后” 的思考。如果一个 ReAct 循环跨越了上百轮工具调用，累积的思考内容可能消耗大量上下文。你会如何修改这个机制来应对超长循环？DeepSeek R1 曾要求剥离全部历史思考，而 DeepSeek V4 反转为强制回传全部 reasoning_content——对比这两种相反的策略，各有什么利弊？这个反转说明了什么？
回答：问题一：针对超长react循环，可以采用分段思考、定期整理形成摘要和外部记忆相结合的策略，只保留近期推理，将历史决策、工具调用及结果压缩存储，按需检索，同时尽量保持固定前缀以复用kv cache；问题二：DeepSeek R1剥离历史思考可以有效降低token 销，但可能损失推理连续性；V4保留了历史思考有利于保存工具推理的内容和状态，但会增加上下文成本，这种反转说明，cot不仅是生成答案的中间过程，也保存了agent的部分记忆。 

3. ★★ 上下文感知压缩实验中，从约 148K 个字符压缩到约 2,000 个字符，这种极端的压缩是否存在“不可逆信息损失”的风险？如何解决？
回答：极端压缩确实可能存在不可以信息损失的风险，因为压缩很容易丢失早期的架构决策、约束、以及失败路径。可以通过这个解决：①首先确定上下文的最重要的关键信息，例如关键的工具使用记录、各类名单等等，并且保证语义完整性；②可以对不同的信息做粗分类，例如检索类任务的上下文尽可能保证广度，分析类任务的上下文有限保留深度

4.  ★★ Agent 状态栏将隐式状态显式化。但如果状态栏本身包含了错误信息（比如工具计数器出了 bug），Agent 可能基于错误的信息做出有害的决策。这种“元信息可靠性”问题如何缓解？
回答：我觉得可以从三点展开：一是状态栏尽可能用代码进行维护，因为llm做归纳总结的能力比不上检索，如果使用llm做状态栏维护，最好是先用llm进行逐条抽取，再用代码进行汇总；二是采用多源信息进行验证，例如工具使用日志、代码执行记录等等；三是有异常可以立马停止操作，提示人工纠正。

5.  ★★ 提示工程消融实验表明，信息组织的混乱导致成功率下降 30% 以上。但在实际开发中，系统提示词往往由多人在不同时间维护。你会用什么工程实践来防止系统提示词的 “熵增”？
回答：可以从三点展开：①采用few-shot示例规范模型的行为；②采用结构化的提示词设计，将提示词拆分为角色的定义、任务规则、工具管理说明和输出规范，避免多人同时修改同一部分；③可以采用git等回滚工具，当提示词不合适时可实现版本回滚，防止提示词的熵增。

6.  ★★★ 本章提出“上下文学习本质上是检索而非推理”。如果这个论断成立，当前所有基于“把更多信息塞进上下文”的优化方向都需要重新审视。你认为应该如何突破这一局限？
回答：我认为突破这一局限的关键，是从单纯增加上下文的大小转向结构化记忆、主动推理和经验学习。首先，通过分层记忆机制整理对话、工具调用和外部知识，减少上下文冗余；其次，引入任务分解、工具验证和反思纠错机制（可以用强化学习），使agent不再只是被动检索，而是主动学习解决问题的方法，提升解决问题的能力；最后，将历史任务中的成功与失败经验转化为可复用策略，并通过训练进一步提升模型的泛化与推理能力。

7.  ★★★ Skills 的渐进式披露只在 Agent 判断需要时才加载完整内容。但这个判断本身依赖模型的能力——如果模型不知道自己不知道什么，就无法正确触发 Skill 的加载。这个“元认知”问题如何解决？
回答：我觉得可以通过明确每一个skill的应用边界，可以引入相关的语义检索工具（例如向量检索、相似度检索等等）以及撰写高质量的few-shot实例（最好能涵盖应用的边界）。此外可以增加独立的skill路由机制，让agent可以根据任务的特征自动搜索相应的skill，而不是完全依赖现有的工具。

8.  ★★ Skills 机制中，Agent 从 SKILL 文件中动态读取提示词之后，后续的操作能否正确遵从这些指令？不同的模型对 Skills 模式的支持有什么区别？
回答：agent动态读取skill文件后，不一定能完全正确遵循指令，因为执行的效果往往受到提示词质量、任务边界、模型指令理解能力及工具调用能力等因素影响。不同模型对skill的支持主要体现在任务识别、复杂指令遵循、多步骤规划和工具调用能力上。通常能力较强的模型能够更准确地触发和执行skill，而能力较弱的模型可能出现漏调用、误调用或执行偏差。

回答：可以采用静态前缀与动态上下文分离的策略，将系统规则和核心工具定义固定在前缀，保证工具顺序与shcema稳定；对于频繁变化的工具，通过工具检索和设计相应的skill路由按需加载，并将时间戳、任务状态等动态信息后置。同时利用版本化管理和增量追加机制，减少前缀失效，提高kv cache的命中率
